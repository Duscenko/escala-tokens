# DEC-2026-11-18-001 · One skill set: account skills are canonical, repo keeps only skills with no account twin

- **Date:** 2026-11-18 · **Owner:** Cesar Durango · **Status:** Decided
- **From:** the AI-readiness review of 2026-11-18 (flags 1–2: "two skill sets, one system"; "`escala-architecture` exists twice and the copies differ").

## Context
Agents working in this repo loaded `.claude/skills/`, which described the old plugin-first flow
(`ds-figma-component`: "the plugin builds the sets", `.figma/manifest.json` with a per-task target file and brand modes).
The account skills describe the current flow (`escala-governance`: one owner per domain, sync agent after approval, the plugin owns nothing).
A generated platform skill was also named `escala-architecture`, the same name as the account skill that holds the Figma ground truth, with different content (brands vs no brands).

## Decision
1. The five Escala account skills are the only source for the Escala design system: `escala-governance`, `escala-architecture`, `escala-component-builder`, `escala-component-docs`, `escala-rebind`. They are never copied into the repo.
2. The generated platform skill is renamed `escala-platform-roles` (folder, `name:`, portable copy). Its description says it is not for the Escala design system.
3. Removed: `ds-figma-component`, `ds-figma-document`, `ds-figma-explain`, `ds-component`, `ds-decide` and `.figma/` (empty maps, wrong target file, "code is canonical for values").
4. Repo-only skills that stay: `escala-figma-to-code`, `escala-platform-roles`, `color-science-core`, plus the external UI-craft set in `skills-lock.json`.

## Consequence
- `.claude/skills/README.md` and `CLAUDE.md` state the rule.
- `scripts/gen-escala-skill.ts`, `src/lib/escalaArchitectureSkill.ts` (`PLATFORM_SKILL_NAME`) and its test write and check the new folder.
- The agent package shipped to users is unchanged (`skills/architecture/`, named `<project>-architecture`).

## Rollback
Revert the commit; `npm run gen:escala-skill` rewrites the old folder.
